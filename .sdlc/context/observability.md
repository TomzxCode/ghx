# Observability

ghx is a local CLI tool, not a hosted service.
There is no production environment, no long-running process to monitor, and no users to alert.
This file records what observability infrastructure actually exists and explicitly scopes out what does not.
Observability skills should treat the missing hosted pillars (metrics, tracing, alerting, dashboards) as out of scope by design, not as gaps to fill.

## Monitoring Pillars

| Pillar | System | Status |
|---|---|---|
| Metrics | `internal/telemetry` (local SQLite recorder, `ghx telemetry summary`) | In use, local-only |
| Logging | `internal/logging` (leveled stderr logging via `--log-level`) | In use |
| Tracing | None | Not applicable |
| Profiling | None (Go test benchmarks and HTML benchmark reports only) | Partial |

No hosted metrics, error-tracking, or alerting system exists.
Nothing in ghx exposes a scrape endpoint, ships to a collector, or reports to a third party.
Telemetry data never leaves the machine unless a user runs `ghx telemetry export` themselves.

## Instrumentation Libraries

| Library | Pillar | Configuration |
|---|---|---|
| `internal/logging` (facade over `log/slog`) | Logging | Global level set by `--log-level debug\|info\|warn\|error`, defaults to info; writes `timestamp level message key=value` lines to stderr without source locations |
| `internal/telemetry` | Metrics | Local SQLite recorder at `~/.local/share/ghx/telemetry.db` (honors `XDG_DATA_HOME`), enabled by default per `.sdlc/knowledge/decisions/1-telemetry-default-on.md`, controlled by `ghx telemetry enable\|disable` |

## Logging

The logging package is a small slog facade.
Lines go to stderr in the format `2006-01-02 15:04:05.000 level message key=value`, so stdout stays clean for command output.
Levels are debug, info, warn, and error, with `warning` accepted as an alias and an empty value meaning info.
The CLI can redirect log output through a writer that coordinates with the cache progress bar (`logging.SetOutput`).

At debug level, read commands log where time goes:

- Repository resolution
- Cache store open
- Token resolution
- The GitHub API list call
- Cache backfill stages

These timing lines are the primary tool for answering "why is this command slow" in an interactive session.

## Local performance telemetry

The telemetry package records one row per API call and cache operation:

- Event kinds cover API calls (`issue_list`, `pr_scan`, `pr_full_page`, searches, and so on), cache hits and misses with the retrieval operation label, and cache store operations (query, load, save).
- Each event stores timestamp, kind, operation, host, repo, HTTP status, duration (including retry backoff), page size, item counts, byte counts, cursor, attempts, retry and failure flags, and rate-limit remaining.
- Recording is asynchronous: events go into a bounded in-memory queue (4096 events, batched 128 at a time, flushed at least every 250 ms) and a single goroutine writes them to SQLite.
- Recording is best-effort: a full queue drops the event and counts it, a sink failure never slows, fails, or changes the exit code of the command that produced the event.
- A disabled recorder is a no-op that keeps the same call sites, so instrumentation has no runtime cost when off.
- The schema is append-only and additive so older and newer binaries can read the same database.

The mock server reuses this data: it can inject latency fitted from recorded telemetry events, so simulated API behavior matches measured per-call costs.

## Log Aggregation

None.
Logs go to stderr and are read by the person (or agent) running the command.
There is no shipper, retention policy, sampling, or structured format beyond the one-line `key=value` layout.

## Tracing

None.
A CLI invocation is a single short-lived process, so there is no cross-service propagation, sampling strategy, or trace backend.
The debug-level timing stages listed above are the closest equivalent within one process.

## Alerting

None.
There is no on-call rotation, uptime target, or alert routing.
The closest health gate is CI (`go vet` plus `go test -race -cover ./...`), which blocks releases rather than paging anyone.
Feature-level observability plans that call for alerts should route them into test failures or CI checks instead.

## Dashboards

No hosted dashboards exist.
The closest equivalents are local inspection surfaces:

| Surface | Location | Purpose |
|---|---|---|
| `ghx telemetry summary` | CLI command (`cmd/telemetry.go`) | Counts, p50/p95 durations, and retry rate by operation kind from the local telemetry database |
| `ghx telemetry export` | CLI command | Exports recorded events for analysis outside the tool |
| HTML benchmark reports | Generated by the benchmark tooling | Before/after performance comparisons for optimization work |

## SLO Reference

No `service-levels.md` exists and none is planned: a local tool has no users to make availability promises to.
Performance targets are handled as non-functional requirements in feature artifacts (for example, the telemetry recorder's per-call overhead budget in `.sdlc/features/25-operational-telemetry/`), not as service SLOs.
